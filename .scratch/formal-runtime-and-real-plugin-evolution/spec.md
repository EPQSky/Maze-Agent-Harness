## 问题陈述

用户希望把现有 Maze Arena 从可运行的开发预览和进化编排框架，提升为可以在本机长期、可信地正式使用的单用户实验工作台。当前仓库已具备实验、比赛、评测、谱系、晋级和 Web 观察能力，但正式启动依赖尚未封装，真实 DeepSeek Harness 尚未安装，模型目录与凭据缺少受控同步流程，比赛镜像没有可复现的构建入口，运行数据和跨存储备份也没有正式管理命令。

更关键的是，当前代码只能证明可编程 Fake Harness 可以穿过编排器模拟一次候选变化，不能证明真实模型会读取反馈、编辑 Generator Plugin 或 Solver Plugin 源码、生成有效构建产物，并通过隔离评测形成可审计晋级。生产适配器只桥接一个外部命令；传给进化智能体的策略记录、可信结果、公开轨迹和隐藏汇总仍为空；自治评测还会在可信 Server 进程中直接加载候选插件。因此，仅补充启动脚本会把未闭环的框架包装成正式产品，却不能满足“插件确实自进化”的核心目标。

## 解决方案

构建一套本机单用户的正式运行层，并完成真实插件自进化闭环。可信控制面继续运行在宿主机，负责 Arena Server、进化编排器、SQLite、插件谱系、模型目录同步、备份和管理命令；不可信 Generator Plugin 与 Solver Plugin 只在摘要锁定的一次性 Docker Match Profile 中执行。正式运行不采用把控制面和 Docker Socket 一并装入应用容器的 Compose 结构。

操作员提供从官方源码固定 Git 提交构建的 DeepSeek Harness、可执行文件和精确版本。正式安装校验并记录这些身份，在本机构建比赛镜像并锁定实际 SHA-256 摘要。模型提供方、模型和 API Key 由 Harness 全局配置管理；Maze Arena 通过显式模型同步读取能力目录和凭据引用，不接收或保存 API Key，也不允许在实验界面录入任意执行端点。

真实进化命令为每次候选尝试创建新的 Harness Session，将冻结冠军工作区、角色约束、允许工具、既往策略记录、可信评测摘要、净化后的公开比赛轨迹和延迟隐藏汇总交给模型。模型必须实际改变允许范围内的可安装运行载荷，并可同时修改测试或追加策略记录，然后显式提交候选。Arena 对源码差异、允许路径、依赖、构建、安装载荷和协议进行验证；无运行载荷变化、只修改测试或策略记录、只修改构建产物或只返回 `submitted` 的响应不得形成有效候选。

候选与冠军必须通过相同的一次性 Docker Match Profile 完成公开和隐藏配对评测。胜出候选写入独立 Git 谱系，创建可校验的晋级标签，并成为下一代冻结冠军；失败和平局候选保留为证据但不替换冠军。正式验收必须以一轮监督式金丝雀实验证明从真实模型响应到下一代冠军继承的完整链路，而不是只证明各组件单独可调用。

## 实现决策

- 保持现有本机单用户产品边界，正式服务只绑定回环地址；不新增身份认证、租户或公网部署能力。
- 可信 Arena Server、进化编排器、SQLite、模型目录管理、备份和插件谱系运行在宿主机。控制面不放入需要 Docker Socket 或等价容器管理权限的应用容器。
- Generator Plugin 与 Solver Plugin 的正式比赛继续采用一次性 Docker Match Profile。所有自治候选的公开、隐藏和展示评测都必须复用该隔离路径，删除可信 Server 直接动态加载候选插件的正式执行路径。
- 操作员显式提供 Harness 源码目录、固定 Git 提交、`dsh` 可执行文件和精确版本。安装与启动不自动克隆、下载或升级 Harness。
- 正式安装记录 Harness 源码提交、可执行文件身份、`dsh --version`、项目构建身份、Match Profile 镜像摘要和资源策略摘要，并把它们纳入健康检查与兼容性判断。
- Match Profile 镜像在本机构建。镜像包含精确 Harness 运行时和正式 Match Profile 所需载荷；Server 配置只接受带 SHA-256 摘要的镜像引用，禁止 `latest` 等浮动标签。
- 提供正式运行管理入口，至少包含 `install`、`doctor`、`models sync`、`start`、`stop`、`status` 和备份操作。首版不默认安装 `systemd --user` 服务，完成验收后再作为独立增强项考虑。
- `doctor` 以关闭失败方式校验运行时版本、Harness 身份、Docker 守护进程与安全能力、镜像摘要、模型导出、bundle 构建、目录权限、数据库可写性和最近完整备份。
- 正式 Web 使用生产构建产物，不运行 Vite 热更新开发服务器。管理入口负责使 Web 与 API 在同一本机访问入口下可用，具体静态文件交付实现保持在运行层内部。
- 可变数据统一放入 `~/.local/share/maze-arena/`，日志放入 `~/.local/state/maze-arena/`，无秘密配置放入 `~/.config/maze-arena/`；数据目录创建为 `0700`，不得依赖源码仓库中的 `.data/`。
- 首版不自行实现磁盘或备份加密。加密由操作系统和备份介质承担；Arena 的配置、日志、SQLite 和备份均不得包含 API Key。
- 备份必须在一致性边界内同时捕获 SQLite、双方 Git 谱系、晋级标签和必要运行清单。备份附带可校验清单，自动保留最近十份；只复制 SQLite 不得标记为可恢复备份。
- 模型提供方、模型、执行端点和真实凭据由 Harness 全局配置拥有。Arena 不新增 API Key 输入字段，也不把任意提供方端点直接传给自治子进程。
- `models sync` 调用受信任的 Harness 导出流程，严格校验 schema、Harness 版本、提供方能力、模型能力和凭据引用，然后原子替换只读目录。目录不自动刷新。
- 新实验从最近一次有效模型目录选择配置。实验启动后继续冻结完整模型配置档；后续模型同步不得改变既有实验。
- 生产 Harness 适配层从“任意外部 JSON 命令”收紧为受版本化协议约束的自治命令适配器。该适配器负责创建新 Session、绑定隔离 home 和候选工作区、应用角色提示与工具策略、传递取消信号，并返回严格结构化结果与可信用量。
- 每次候选尝试从冻结冠军提交物化新工作区。模型只能修改己方插件允许范围；工作区不继承 `.git`、`node_modules`、旧构建缓存或其他 Session 状态。
- 进化输入不再使用空占位数据。编排器从插件谱系和可信数据库组装既往策略记录、候选结果、净化后的公开轨迹与延迟隐藏汇总，并应用现有对手控制文本排除规则。
- `submitted` 只表示模型请求进入候选验证，不表示候选有效。验证器必须检测允许范围内的可安装运行载荷变化；测试和新策略记录可以伴随候选，但不能单独使候选有效。无运行载荷变化、仅构建产物变化、保护文件变化、依赖漂移或超出配额均拒绝。
- 构建产物必须由可信构建步骤从候选源码重新生成。候选提交和正式评测使用同一受验证内容身份，不能直接信任模型写入的 `dist`。
- 公开门禁可向同一候选尝试返回净化、类型化诊断，并允许现有上限内的修复轮次。隐藏评测只执行一次，不向当前候选返回种子或完整轨迹。
- 候选与冠军使用冻结的对手提交、案例顺序、资源策略和镜像摘要执行配对评测。晋级继续服从现有公开退化门禁、隐藏比较、平局不晋级和角色专用评分规则。
- 所有有效候选均写入对应角色的独立 Git 谱系。只有胜出候选更新冠军并创建附注晋级标签；下一代必须从更新后的冠军提交物化工作区。
- 正式基线验收增加“真实自进化金丝雀”步骤。金丝雀必须证明真实提供方调用、候选源码差异、可信重建、Docker 评测、Git 候选证据及下一代起点；候选是否必然胜出不作为模型能力保证，但系统必须准确记录晋级或拒绝原因。
- Fake Harness 保留为日常确定性测试工具，任何界面、日志或验收报告都不得把 Fake Harness 运行描述为真实插件自进化。
- 现有 SQLite 与 Git 双权威、实验冻结、密封评测、晋级标签、防篡改恢复和单活动实验约束保持不变。

## 测试决策

- 主要测试接缝采用正式运行管理 CLI 的黑盒边界，并把一轮完整自治进化作为最高层场景：在隔离用户目录中安装、同步模型、启动服务、创建并验收实验、运行一代、停止、备份和恢复，只观察命令退出码、HTTP 可见状态、Git 证据、比赛事件和持久化结果，不断言内部类结构。
- 日常端到端测试使用遵循生产自治命令协议的确定性 Harness 夹具。夹具必须通过与真实 Harness 相同的工作区和工具边界修改插件源码，不能在测试代码中直接复制 `dist` 或绕过候选构建。
- 完整闭环测试断言：冠军源码被物化；候选源码发生允许变化；可信构建重新生成产物；候选与冠军通过 Docker Match Profile 配对评测；候选提交进入 Git 谱系；胜出时创建晋级标签；下一代工作区内容来自新冠军。
- 负向闭环测试覆盖只返回 `submitted`、完全无变化、只修改测试或策略记录、仅修改 `dist`、修改依赖、修改保护文件、超出载荷、构建失败、协议失败、非确定性和评测失败，并断言这些情形不会替换冠军。
- 进化输入测试从外部可见的 Harness 请求夹具检查既往策略记录、可信结果、公开轨迹和隐藏聚合已提供，同时断言隐藏种子、完整隐藏轨迹、对手源码及对手控制自由文本没有进入请求。
- 正式运行 CLI 测试覆盖重复安装、重复启动、重复停止、活动进程状态、陈旧 PID、异常退出恢复和部分初始化清理，并断言命令幂等且失败信息可操作。
- `doctor` 表驱动测试覆盖 Node/pnpm/Git/Docker 缺失或版本错误、Harness 提交或版本不匹配、可执行文件替换、镜像浮动标签、摘要不匹配、模型目录损坏、目录权限过宽、数据库不可写和缺少完整备份。
- 模型同步测试使用多个能力不同的假提供方，覆盖原子替换、目录结构拒绝、未知字段、凭据引用、同步失败保留旧目录，以及新目录不改变已冻结实验。
- 备份测试在真实临时 SQLite 与 Git 谱系上创建候选和晋级标签，执行备份与恢复后校验数据库事实、提交、标签对象和摘要一致；单文件数据库副本必须被恢复检查拒绝。
- 日志和配置测试向环境、Harness 错误和模型响应注入伪 API Key，断言管理输出、日志、模型目录和备份均不包含该秘密。
- Match Profile 继续复用现有进程协议和正式隔离策略测试作为底层先例，扩展真实 Docker 镜像摘要、候选挂载、网络禁用、只读文件系统、非 root、CPU、内存和清理验证。
- Server 继续复用现有实验工作台 API、模型配置冻结、生产 Harness JSON 桥接、自治运行时、重启恢复和双权威测试作为先例，但原先通过直接复制构建产物模拟进化的测试只能作为历史回归，不能作为真实自进化验收证据。
- Web 继续复用现有工作台 Playwright 测试，新增正式生产构建入口的最小冒烟，断言实验状态、候选差异、晋级证据和失败原因可观察，不要求测试内部组件实现。
- 真实 DSH 与真实模型提供方不进入日常确定性测试。操作员监督的正式验收使用低预算金丝雀实验，断言真实模型确实修改源码且完整链路可审计；非确定性模型文本和是否产生更优算法不作为黄金断言。
- 好测试只断言用户可观察行为、安全边界、持久化事实和跨组件契约。不得通过 mock 私有方法、检查内部字段或仅断言某函数被调用来证明插件自进化。

## 不在范围内

- 多用户认证、授权、租户隔离、局域网或公网暴露、托管服务和分布式执行。
- 把可信控制面放入持有 Docker Socket 的 Compose 应用容器，或采用 Kubernetes、远程容器编排和微型虚拟机。
- 安装程序自动发现、下载或升级 DeepSeek Harness；操作员必须提供明确来源和锁定身份。
- 在 Maze Arena 中保存 API Key、管理提供方账户、实现通用秘密管理器或接受任意未经 Harness 登记的模型端点。
- 后台自动刷新模型目录，或让目录变化修改运行中和已冻结实验。
- 首版默认安装开机常驻服务；`systemd --user` 属于完成正式运行验收后的独立增强。
- 应用层磁盘加密、备份加密、云备份、跨机器同步、远程归档和灾难恢复编排。
- 保证每个真实模型候选必然优于冠军。规格保证真实修改、严格评测和正确晋级，不保证外部模型一定产生算法进步。
- 放宽现有实验冻结、隐藏评测密封、平局不晋级、资源限制、单活动实验或 Git/SQLite 双权威规则。
- 允许进化智能体修改 Arena、评测、协议、Harness 核心、依赖集合、对手插件或其他可信组件。
- 在正式比赛期间调用模型，或把远程模型响应直接作为比赛动作。
- 用 Fake Harness 运行冒充真实自进化，或把只生成文本说明、只修改构建产物和只创建空提交计为有效进化。
- 本规格直接拆分或实施具体任务票据；后续由 `$to-tickets` 生成依赖有序的纵向票据。

## 补充说明

- 本规格于 2026-09-03 根据正式使用访谈、领域词汇表、已接受 ADR 和当前实现审计形成。
- 当前实现已经具备自治代循环、候选提交、配对评测、晋级标签和下一代冠军引用的主要编排结构，但真实 Harness 自治命令、有效反馈输入、可信重建和 Docker 自治评测仍是正式使用阻塞项。
- “插件会自进化”在本规格中具有可验证含义：真实模型在受限工作区改变己方插件的可安装运行载荷，候选从受控源码可信重建，经冻结且隔离的配对评测形成 Git 证据，并在胜出时成为下一代冠军。仅调用模型、生成计划、只改测试或策略记录、或产生空提交不满足该定义。
- 模型具有非确定性，金丝雀候选可能未晋级。此时只要候选确有允许范围内的源码变化、完成可信构建和隔离评测，并留下准确失败或平局证据，即可证明进化机制工作；算法改进能力需通过后续多代实验观察。
- 已接受的部署与集成决策记录在 ADR 0006、0013、0016 和 0029；本规格不改变这些决策。
- 本规格是父级规划交付物，不带 `ready-for-agent` 状态。实现范围、依赖、验收标准和票据状态由后续 `$to-tickets` 负责。
